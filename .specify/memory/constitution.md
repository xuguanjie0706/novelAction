# multi-agent-demo 项目宪章

## 核心原则

### I. 控制面主轴（不可违背）

产品在每个集成表面上 MUST 呈现 **一条用户可见的对话主线** 与 **一套主事件契约**。新能力 MUST 挂接到
`docs/tech/RFC-session-control-plane.md` 与 `docs/tech/ARCHITECTURE_ONE_PAGER.md` 所定义的 Session、Message、Run
语义，不得在无迁移方案与读路径「唯一真相」说明的情况下另起一套「第二个产品」式 API。

**理由**：避免 HITL、LangGraph、page-agent 在体验与客户端代码上继续分叉。

### II. 跨运行时变更须契约先行

凡跨越 **编排器、工作流运行时、委托运行时或客户端流** 的改动，在大范围重构前 MUST 明确验收场景、
**幂等**（如客户端消息键）、**取消传播**、**超时与循环上限**。规格书中记录的决定 MUST 与
`ARCHITECTURE_ONE_PAGER.md` §8.2–§8.3、§9 一致。

**理由**：避免 WebSocket、worker、浏览器委托对生命周期各说各话导致返工。

### III. 切片交付与双写纪律

大型迁移 MUST 以 **切片增量** 交付（特性开关或单路径试点）。新旧路径并存期间，团队 MUST 书面说明
**读路径以哪套存储或 API 为准** 以及 **收敛** 预期。

**理由**：与 `readme.md` 分阶段蓝图（P0→P1→P2）一致，降低生产环境不一致。

### IV. 安全与隔离基线

功能 MUST 保持 **按用户隔离的数据访问**、**密钥卫生**（默认不向日志或模型上下文泄露密钥），以及
工具、MCP、页面委托的 **信任边界**，与 `readme.md` 阶段 0–2 及 RFC 安全主题一致。

**理由**：平台已超出 demo，运维与滥用风险真实存在。

### V. 可观测、可测试的交付物

每份功能规格 MUST 包含 **可独立验证的用户场景**、带清晰验收条件的 **功能需求**，以及 **不依赖实现术语**
即可度量的 **成功标准**。契约或事件形态变更在进入主交付合并前 SHOULD 具备 **清单或自动化检查**
（在 specify 流程要求时 MUST 先过清单再进入 plan）。

**理由**：支撑规范驱动交付与异步、多组件流程的回归安全。

### VI. 规格闭包与完整交付

凡标记为 **实现中** 或 **待合并** 的规格，进入默认分支的代码与配置 MUST **闭环**该规格之功能需求与成功标准：
可在目标环境中 **复现验证**（手工按 quickstart 或自动化测试）；MUST 附带 **发布说明或运维可见文档**
（含已知限制、环境变量、FR-006 类「委托是否收到停止」等）。禁止长期停留在「仅有 plan/tasks、无验收路径」
的分支状态而不合并或不明示搁置原因。

**理由**：「完整交付」指 **约定范围内的可发布闭包**，与原则 III 的切片不矛盾；避免文档与主线永久脱节。

## 架构对齐

本仓库权威架构引用：

- `docs/tech/ARCH.md` — 当前模块图
- `docs/tech/RFC-session-control-plane.md` — 目标控制面、TaskPlan、工具注册表（草案）
- `docs/tech/ARCHITECTURE_ONE_PAGER.md` — 主轴浓缩、§8 横切清单、§9 开发准入
- `readme.md` — 分阶段产品化顺序，对照 `docs/PRODUCTIZATION.md`

实现不得与一页纸中的 **单主轴** 与 **委托/浏览器** 规则相冲突；若需偏离，须先修订 RFC 与本宪章。

## 研发流程与质量门禁

1. **Speckit 流程**：`/speckit.specify` → `/speckit.plan` → `/speckit.tasks`（按需）；spec 清单在 specify
   命令要求时 MUST 在规划前通过。
2. 触及运行时编排、WebSocket 载荷或 HITL/浏览器交还的 **PR**，若行为变化，MUST 在同一变更集中引用
   所依据的现行 spec 或 RFC 章节。
3. **复杂度**：对同一路用户旅程新增并行代码路径 MUST 在 spec 或 plan 中论证；优先采用开关后的适配层，
   而非长期分叉。
4. **合并前**：对照原则 **VI** 核对是否具备可执行验收与对外说明，再合并默认分支。

## 治理规则

1. 本宪章 **高于** 临时编码偏好。
2. **修订**：以 PR 更新本文件，按下条规则递增版本，并在门禁变更时同步 `plan-template.md` 中的宪章检查项。
3. **版本语义**：
   - **MAJOR**：删除或与不兼容方式重定义某条原则。
   - **MINOR**：新增原则或实质性新增强制门禁。
   - **PATCH**：措辞、澄清、非语义修正。
4. **合规**：当变更触及 API 表面、持久化、流式通道或委托时，评审者 SHOULD 对照核心原则 **I–VI** 核查。
