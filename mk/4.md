# 系统全面审查报告
**以架构师、作家、总编辑三重视角**

---

## 一、已做得非常好的部分

### 【架构师视角】真正落地的分层设计

Bootstrap 系统是整个项目最干净的模块。14 个步骤各自一个文件，行数全部在 300 行以内，`graph.py` 作薄壳只做调度，`parse.py` 统一解析，`retry.py` 统一重试——这才是「编排薄壳模式」真正落地的样子。番茄专属的 `graph_fanqie.py` 独立图、9 阶段、18 步，完全不污染通用流程，隔离做得相当漂亮。

`services/ai/` 的拆分也执行到位：`context_builder`、`sampling`、`quality`、`debrief`、`draft_stream`、`coherence`……按业务能力切包，`AIService` 瘦壳聚合，不再是上帝类。

多租户安全做到了正确的地方：`main.py` 用 `_project_scoped_dep = [Depends(verify_project_access)]` 统一把守所有项目级路由，不是每个路由自己校验，这是正确的架构位置。

RAG/Embedding 服务的设计非常成熟：`fire-and-forget` 不阻塞主请求、pgvector 不可用时优雅降级、时效衰减公式（`1 / (1 + α * chapter_distance)`）体现了对网文长篇的深刻理解——越远的记忆越低权重，比平铺检索要聪明得多。

`GenerationJob` + `draft_graph` 的引入代表了架构上的一次重要跃升：任务生命周期与 HTTP 连接解耦，断线重连 replay，human interrupt 跨请求通信——这是真正的生产级设计，不是 Demo 级。

`outline_linter` 六套规则（CH/SEQ/VL/OC/RP/CM）独立文件 + gate 阻断 + repair-seed 修复工作流，是目前整个系统里代码最整洁、设计最清晰的子系统。

### 【作家视角】懂网文的设计

`phase` 字段（opening/rising/turning/dark_hour/climax/ending）不是摆设，它直接驱动：采样温度分档（`draft.opening` 0.95、`draft.dark_hour` 0.75）、字数预算（至暗期 ~2800 字、高潮期 3000-3300）、写章 prompt 切模板。这说明系统的设计者真正理解网文节奏，不是照搬通用写作工具。

Scene 三层调度（章纲→分场→逐场正文）是对网文「分场不出戏」问题的正确回答。网文最大的 AI 味来源之一是场景跳切，有了 `pov_character_id`、`goal`、`conflict`、`turn`、`hook_strength`、`word_budget`，AI 才有真正可量化的约束。

伏笔台账（`Foreshadow` 模型）的「埋/加热/收」三态 + 双向关联（`foreshadows_laid`/`foreshadows_resolved`）+ Bootstrap 自动写入，是对「伏笔失忆」问题的系统性解答。大部分 AI 写作工具伏笔完全靠 AI 自由发挥，这个设计强多了。

`positioning`（Step 0 立项会议）在所有写章 prompt 里作为硬约束注入（target_audience、face_slap_pattern、pace_type），这是防止 AI 写着写着「文艺化漂移」的关键防线。

### 【总编辑视角】质控链完整

追读意愿曲线（`RhythmMapPage`）+ 钩子强度检测 + 故事线悬空检测 + 章末承诺比对，已经是一套比较完整的「编辑台」。多次分析取均值（`chapter_analysis_records`）的设计体现了对 AI 评估不稳定性的清醒认知。

`QualityDebt`（质检欠债台账）+ `quality_debt_micro_patch`（微修复）的分离，是「发现问题」和「解决问题」解耦的正确设计，不会因为一次修复失败就丢失债务记录。

## 二、文档说「已完成」但实际存在缺口的部分

### 【架构师视角】两套写章架构并存，没有明确主次

这是当前最大的架构风险。系统中同时存在：
- **旧路径**：`draft_routes.py` + `gated_draft_routes.py`（StreamingResponse，HTTP 请求生命周期绑定）
- **新路径**：`jobs.py` + `services/draft_graph/`（LangGraph，异步任务队列，WS 断线重连）

前端 `ChapterEditor` 用的是哪条路径？`ScenePipelinePanel` 用的是哪条？现在代码里两条路径都在跑，新架构的优势（断线重连、human interrupt、任务持久化）只有新路径才有，但旧路径并没有被标记为 deprecated 或被前端迁移。这不是「备选」，这是「两套生产代码同时维护」，是技术债的定时炸弹。

### `emotion_arc` / `villain_arc` 有生成，无注入

Bootstrap Step 9.5 生成情绪节律图，Step 9.8 生成反派行动线，都写入了 `Project.extra`。`context_new_steps.py` 也有对应的 `_build_emotion_arc_block` 和 `_build_villain_arc_block`。但检查 `draft_stream.py` 和 `draft_routes.py` 的实际写章上下文构建流程：这两块**没有被注入到正文写章的 prompt 里**。换言之，花了大量 Token 生成的情绪节律图和反派行动线，只是存在数据库里，对实际写章没有任何影响。`positioning` 注入了，`reader_promise` 注入了，但这两个更高维度的叙事约束没有。

### `Location` 模型做了，写章约束注入只在 `gated_draft_routes` 里

`Location` 模型完整，CRUD 路由完整，前端 `LocationsTab` 完整，`gated_draft_routes._build_location_context` 也有注入逻辑。但主写章路径 `draft_routes.py` / `draft_stream.py` 没有调用这个函数。`Scene.location_id` 外键虽然预留了，但前端 `ScenePipelinePanel` 创建 Scene 时传的是 `location_name` 文本，不是从 Location 库里选择——感官基准的「空间连续性」承诺还没有真正兑现。

### `ReaderPromise` 深度闭环：「自动」名不副实

代码里 `auto_debrief` 端点存在（`POST /ai/auto-debrief`），写章时也注入了 open 承诺。但「auto」的部分是：用户完成一章后，需要**手动调用** `auto_debrief` 接口，才会触发 AI 识别新增/兑现的承诺。没有任何地方在章节保存时自动触发这个流程。文档说「深度闭环待完善」，但用户在用的感受是：承诺台账是个「只进不出」的口袋，写了 30 章后 open 承诺积累成堆，没有任何提示。

### `vol_chapter_plans.py` 527 行，接近红线且逻辑过重

这个文件同时承担：预算计算、卷间钩子承接、foreshadow 同步、linter 阻断、quota 累计。远不止「一个步骤」，实际上是 3-4 个步骤的逻辑压缩在一起。接近 600 行硬上限，且每次新增约束都会往这里加。

## 四、需要完善的核心短板

### 【总编辑视角】最重要的一条：写章前没有「当前状态快照」

一个编辑在发回稿件前，脑子里是有这一章的完整背景的：主角现在在哪、什么心情、上一章结尾留了什么悬念、对手最近在干什么。系统现在有 `reader_promise`、`memory_chunks`、`outline_node`、`quality_debt`，但独独缺少一个「本章写作前的人物当前状态快照」注入——主角当前境界、当前位置、当前情绪基调、核心矛盾进展到哪一步。这些散落在 `Character` 表的各个字段里，但没有一个专门的「本章前状态」聚合注入到 prompt。这是 AI 味的一个重要来源：每章开头都像在介绍一个陌生人。

### 【架构师视角】缺乏跨章节一致性校验（运行时）

Bootstrap Step 14 做的是全量一次性一致性扫描，是静态的。但每次写完一章后，没有增量的一致性校验：这章里出现的人物是否还活着？使用的技能是否符合当前境界？这章里新引入的设定和之前有没有矛盾？`outline_linter` 解决的是大纲层面的静态检查，`quality.py` 做的是文本质量评估，但两者之间缺少一个「写完一章后的增量设定一致性触发器」。`CharacterChangeLog` 模型存在，说明设计者意识到了这个问题，但还没有把它接入自动校验链路。

### 【作家视角】Dialog/Voice 一致性没有保障

所有人物有 `speech_style`、`speech_kit`（标志性词语、样本台词、内心独白），这是好的。但没有机制保证 AI 在写张三说话时真的用了张三的腔调。质检维度里没有「人物声音一致性」这一项。编辑视角最痛恨的一件事——主角突然像反派说话、反派突然用主角的腔——系统没有任何防线。

### 【架构师视角】生成任务队列缺少优先级和并发控制

`GenerationJob` 有 `pending → running → completed` 状态机，但没有优先级字段，没有并发槽位控制，没有限速。如果用户同时提交 10 个章节生成任务，系统会同时发起 10 路 LLM 请求，既可能触发 API 限速，也可能因资源竞争导致所有任务都变慢。`user_credit` 系统存在，但没有接入任务队列层面的限流。

### 番茄专属流程与通用流程的同步问题

`graph_fanqie.py` 独立图很好，但通用 bootstrap 每次新增功能（比如 emotion_arc、villain_arc、core_mysteries），番茄图都没有同步更新。两套图的能力差距会越来越大，最终变成两套需要独立维护的产品线，而不是「针对番茄的优化版本」。

## 五、优先级建议

**必须立即处理（P0）：**

两套写章架构并存的问题。在前端明确标注「旧路径将废弃」，并给出迁移时间线，否则维护成本会指数级增长。

`emotion_arc` 和 `villain_arc` 注入写章。这两个数据已经花了 Token 生成了，但对实际写章质量没有贡献，是最直接的「性价比缺口」。

**重要但可规划（P1）：**

前端五个超限组件的拆分，按照 CLAUDE.md 里已写好的蓝图执行就行，不需要再设计，只需要做。

`ReaderPromise` 自动触发：在章节保存成功后（或用户手动触发「复盘」时），自动调用 `auto_debrief`，才能让承诺台账真正成为活的追踪系统，而不是一个只增不减的待办列表。

写章前人物当前状态快照注入。

**长期规划（P2）：**

`Project.extra` JSON 重构为独立表或有 schema 约束的结构。EPUB 导出。前端测试体系。跨章节增量一致性触发器。番茄/通用图功能同步策略。

这个系统的设计水准在 AI 写作工具里是相当靠前的，尤其是 Bootstrap 的模块化、RAG 的时效衰减、phase 驱动的采样策略、outline linter 的规则体系。核心问题不是功能缺失，而是：**已生成的高质量数据（emotion_arc、villain_arc）没有闭合回写章链路**，以及**前端欠下的重构债务在持续阻碍新功能的安全交付**。这两件事解决好，系统就能从「Demo 级完整」升级到「生产级可靠」。
